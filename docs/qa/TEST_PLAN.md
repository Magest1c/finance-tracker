# План тестирования Finance Tracker API

## 1. Цель

Проверить, что REST API Finance Tracker корректно обрабатывает аутентификацию, финансовые ресурсы пользователей, фильтрацию транзакций и месячные отчёты. Стратегия сочетает интеграционные и API-тесты на Go, проверку контракта и дымовое тестирование контейнера.

## 2. Область тестирования

Входит в область тестирования:

- состояние и доступность сервиса;
- регистрация и вход;
- аутентификация по Bearer-токену;
- счета и категории;
- создание, получение, фильтрация, изменение и удаление транзакций;
- месячный финансовый отчёт;
- валидация входных данных и контракт HTTP-ответов;
- проверка владельца ресурсов и защита от нарушения контроля доступа;
- валидность документа OpenAPI;
- запуск приложения в контейнере.

Не входит в текущую версию:

- постоянное хранение данных и миграции БД — хранилища намеренно работают в памяти;
- токены обновления, выход из системы и срок действия токена;
- нагрузочное тестирование в условиях, близких к промышленным;
- браузерный интерфейс и доступность;
- конвертация валют.

## 3. Уровни и виды тестирования

| Уровень или вид | Инструмент | Назначение |
|---|---|---|
| Интеграционное тестирование обработчиков | Go `testing`, `httptest` | Быстрые детерминированные проверки маршрутизации, валидации и бизнес-правил |
| API-тестирование по методу чёрного ящика | Go `testing`, `net/http` | Проверка наблюдаемого поведения отдельного работающего процесса по HTTP |
| Контрактное тестирование | Go, `kin-openapi` | Обнаружение ошибок в документе OpenAPI 3.1 |
| Негативное тестирование безопасности | Go | Отсутствующий токен, чужие ресурсы, одинаковые ошибки входа |
| Статический анализ | `gofmt`, `go vet` | Форматирование и поиск распространённых дефектов Go |
| Обнаружение гонок данных | `go test -race` | Проверка конкурентного доступа к хранилищам в памяти |
| Дымовое тестирование контейнера | Docker, `/health` | Проверка запуска собранного образа и обработки запросов |

## 4. Тестовое окружение

- версия Go берётся из `go.mod`;
- локальный API: `http://127.0.0.1:<свободный-порт>`;
- CI: предоставляемый GitHub runner с Ubuntu;
- хранилище: структуры данных в памяти, очищающиеся при перезапуске процесса.

Go-набор по методу чёрного ящика выбирает свободный локальный порт, собирает API-бинарник, запускает его, до 30 секунд ожидает успешный ответ `/health`, выполняет HTTP-тесты и завершает процесс.

## 5. Критерии начала тестирования

- зависимости проекта доступны для загрузки;
- приложение на Go компилируется;
- тестовое окружение может открыть локальный сетевой порт.

## 6. Критерии завершения тестирования

- все тесты на Go пройдены;
- проверка OpenAPI пройдена;
- `go vet ./...` не обнаруживает проблем;
- детектор гонок Go не обнаруживает гонок данных;
- Docker-образ собирается, а `/health` возвращает HTTP 200;
- в реализованной области нет открытых блокирующих или критических дефектов.

## 7. Риски и меры снижения

| Риск | Последствие | Мера снижения |
|---|---|---|
| Общее состояние в памяти | Взаимное влияние тестов | Отдельный процесс для Go black-box набора и новый экземпляр приложения для каждого интеграционного Go-теста |
| Конфликт динамического порта | Нестабильный запуск | Получение свободного порта интерфейса обратной петли до старта процесса |
| Неопределённый порядок обхода map | Нестабильные клиенты и тесты | Сортировка счетов и категорий по `id`, регрессионные тесты порядка |
| Обход аутентификации | Доступ к данным другого пользователя | Промежуточный обработчик Bearer и проверка соответствия пользователя и владельца ресурса |
| Неоднозначные границы дат | Ошибочные месячные суммы | Полуинтервалы `[from, to)` и временные метки RFC3339 |
| Большое тело запроса | Избыточное потребление памяти | Ограничение JSON-запроса размером 1 МиБ |

## 8. Жизненный цикл дефекта

1. Воспроизвести дефект на исходной версии.
2. Зафиксировать ожидаемый и фактический результат, серьёзность и приоритет.
3. Добавить регрессионный автотест, падающий до исправления.
4. Исправить дефект.
5. Запустить полный контроль качества.
6. Перевести дефект в статус «Исправлен» только после успешной регрессии.
